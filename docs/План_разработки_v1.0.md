### 1.2 Паттерны, которые нужно соблюдать

| Что | Как принято в проекте |
|---|---|
| Роутер сущности | `makeCrudRouter({entity, model, roles, createSchema, include, buildWhere, search, validate, transform, prepareData})` |
| Ответ клиенту | всегда через `serialize(...)` — Prisma `Decimal` → number, `Date` → ISO |
| Ошибки | `throw notFound('…')`, `badRequest`, `forbidden`; обработчик — `asyncHandler` |
| Права | `requireAuth` + `requireRole('operator','admin')` / `requireAdmin` — **на сервере**, не только в UI |
| Аудит | `writeAudit(req, {action, entity, entityId, before, after}, tx)` в той же транзакции |
| Деньги | `Decimal @db.Decimal(14,2)`, округление — `round2()` из `services/compute.ts` |
| Даты | хранятся как UTC-полночь; сравнения — полуоткрытый интервал `[from, toExclusive)`, как в `kpi.service.ts` |
| Мягкое удаление | `deletedAt` / `deletedBy`, выборки всегда с `deletedAt: null` |
| Клиентские запросы | `useList(entity, params)` и `useCrudMutations(entity)`; новые ключи добавлять в `RELATED_KEYS` |
| Меню | пункт добавляется в `SECTIONS` в `Layout.tsx` + маршрут в `App.tsx` |

### 1.3 Критично: как применяется схема БД

Прод (`Dockerfile`, Render) запускается командой:

```
npx prisma db push && npx prisma db seed && npx tsx src/index.ts
```

`db push` **без** `--accept-data-loss`. Отсюда жёсткие правила:

- **Только аддитивные изменения схемы.** Новые модели и новые поля.
- Новое поле в существующей модели — **только** `nullable` или с `@default`. Иначе деплой упадёт на непустой таблице.
- **Никаких переименований и удалений** существующих полей и моделей.
- Проверять локально: `docker compose up --build` на копии базы, а не на рабочей.

### 1.4 Что нельзя трогать

| Файл / поведение | Почему |
|---|---|
| `services/compute.ts` (`computeOperation`, `round2`) | На нём держатся касса, дашборд, KPI. Новый модуль его **использует**, но не меняет |
| `services/kpi.service.ts` | KPI менеджеров — отдельная логика, не пересекается с выплатами врачам |
| `Operation.surgeon`, `Operation.anesthesiologist` | Используются в фильтрах, экспорте и отчётах. Остаются и продолжают заполняться (см. Э1-3) |
| Существующие маршруты `/api/*` | Ответы не менять — только добавлять новые поля при необходимости |
| Сид демо-данных | В проде демо не создаётся; новый сид не должен это ломать |

### Э0-4. API схем выплат с версионностью

**Файлы:** `server/src/routes/payouts/schemes.ts`, `server/src/services/payout-scheme.service.ts`

Правила:

1. `POST /api/payouts/schemes` — создаёт схему **или новую версию** существующей: у предыдущей версии проставляется `validTo = validFrom − 1 день` и `replacedById`, у новой `version = prev.version + 1`.
2. `PUT` для изменения условий **не реализовывать** — правка только созданием версии. Разрешить PUT лишь для `name` и `note`.
3. Валидация: периоды действия схем одного врача не пересекаются; `validFrom` не может попадать внутрь периода, по которому уже есть выплаченная ведомость (проверку включить на этапе 3, до этого — TODO с явным комментарием).
4. `getSchemeForDate(payeeId, date)` — возвращает версию, действовавшую на дату операции. Это единственный способ получения схемы в расчёте.

**Готово, когда:** создание второй версии закрывает первую; `getSchemeForDate` на дату из прошлого возвращает старую версию; попытка создать пересекающийся период даёт понятную ошибку на русском.

### Э1-3. Синхронизация участников со старыми полями

**Файлы:** `server/src/routes/operations.ts`

В `createSchema` добавить массив `participants: [{payeeId, role, sharePct?, anesthesiaType?, shiftDay?, shiftNight?}]`.

**Главный источник — поле формы `surgeon`** (решение от 19.08.2026). Строковые поля `Operation.surgeon` и `Operation.anesthesiologist` остаются ведущими для KPI, экспорта и фильтров; участники сохраняются рядом и этих полей не переписывают.

В `prepareData` / `afterCreate` / `afterUpdate`:

- создавать и обновлять участников в **той же транзакции** (`ctx.tx`);
- **проверять согласованность:** если у участника с ролью `surgeon` поле `dictionaryLabel` заполнено и не совпадает с `Operation.surgeon` — отклонить сохранение с понятной ошибкой на русском. Если `dictionaryLabel` пустой — сохранить, но пометить операцию для блока «Сигналы» («получатель без привязки к справочнику»);
- валидировать: если участников с ролью `surgeon` больше одного, сумма `sharePct` = 100.

**Почему не «выводить из участников»:** это поставило бы экспорт и KPI в зависимость от заполненности `dictionaryLabel` у каждого получателя — один незаполненный, и в выгрузке молча появляются операции без хирурга.

**Важно про анестезиолога:** поле `Operation.anesthesiologist` — обычная строка без проверки по справочнику (`optionalString`), в отличие от `surgeon`. Для расчёта выплат анестезиологу источником всегда является участник, строковое поле остаётся справочным.

**Готово, когда:** после сохранения операции с участниками поле `surgeon` совпадает с участником-хирургом; попытка сохранить расхождение через API отклоняется; страница KPI менеджеров и выгрузка операций в Excel дают те же цифры, что до изменений (проверить на копии базы «до/после»).

## ЭТАП 2. Движок начислений

Цель: система считает начисления событийно и идемпотентно.

### Э2-1. Чистая функция расчёта

**Файлы (новый):** `server/src/services/payout-calc.service.ts`

```ts
export interface CalcInput {
  operation: {...}; payments: {...}[]; scheme: {...};
  acquiringRates: {...}[]; materialsFact: number | null; materialNorm: number | null;
}
export interface CalcOutput {
  base: number; components: ComponentLine[]; sharePct: number;
  baseForShare: number; amountFull: number; calcTrace: TraceLine[];
}
export function calcPayout(input: CalcInput): CalcOutput
```

Требования:

- **Без обращения к БД** — всё приходит параметрами. Это делает функцию тестируемой.
- Порядок: вычеты «до доли» → доля → вычеты «после доли».
- Комиссия: сумма по платежам, ставка терминала **на дату платежа**; при отсутствии ставки — `throw badRequest('Не задана ставка эквайринга для терминала «…» на дату …')`.
- `calcTrace` — массив читаемых строк для экрана «Как посчитано» (см. 8.4 ТЗ).
- Округление только на выходе, через `round2()`.

**Готово, когда:** проходят тесты Т1–Т4 и Т7 (числа из ТЗ воспроизводятся точно), включая Т6 (снятая галочка «Расходные материалы» даёт 736 750).

### Э2-2. Событийный движок

**Файлы (новый):** `server/src/services/payout-engine.service.ts`

```ts
export async function recalcOperation(operationId: number, tx: PrismaClientOrTx): Promise<void>
```

Алгоритм:

1. Загрузить операцию, участников, платежи (без удалённых), списания, схему на дату операции.
2. Для каждого участника-получателя посчитать `amountFull` через `calcPayout`.
3. Пройти платежи по возрастанию даты, накопительно считая коэффициент оплаты; для каждого платежа определить дельту начисления.
4. Сверить с уже существующими начислениями по операции:
   - начисления со статусом `locked` / `paid` **не трогать никогда**;
   - `free`-начисления привести к расчётным значениям (обновить или создать недостающие);
   - если из-за возврата или правки итог меньше уже заблокированного — создать **корректировку** с `eventDate = сегодня`, `isCorrection = true`.
5. Если схемы нет — начисления не создавать, операцию пометить для блока «Сигналы».

**Готово, когда:** трёхкратный запуск подряд не меняет данные (Т17); частичная оплата в разных месяцах даёт две записи без задвоения (Т12).

### Э2-4. Массовый пересчёт и предпросмотр схемы

**Файлы:** `server/src/routes/payouts/calc.ts`

- `POST /api/payouts/recalculate` — `{from, to}` либо `{operationIds}`; пакетная обработка, возврат сводки «обработано N операций, создано M начислений, пропущено K (нет схемы)».
- `POST /api/payouts/schemes/:id/preview` — прогон новой версии схемы на последних 10 операциях врача, ответ «было / стало / разница» + средний процент отклонения.
- Регламентный пересчёт за последние 90 дней: отдельный маршрут + кнопка в интерфейсе. Автозапуск по расписанию — опционально (в проекте планировщика нет; при необходимости добавить GitHub Actions по образцу `.github/workflows/db-backup.yml`).

**Готово, когда:** пересчёт 500 операций укладывается в 5 секунд; предпросмотр показывает разницу до сохранения схемы и предупреждение при отклонении больше 20%.

## ЭТАП 3. Ведомости

### Э3-1. Схема БД: ведомости

**Файлы:** `server/prisma/schema.prisma`

`PayoutSheet`, `PayoutSheetLine`, `PayoutPayment`; в `PayoutAccrual` — `status`, `sheetId`.

**Готово, когда:** `db push` проходит; существующие начисления получают статус `free`.

### Э3-2. Сервис ведомостей

**Файлы:** `server/src/services/payout-sheet.service.ts`, `server/src/routes/payouts/sheets.ts`

- `previewSheet({kind, from, to, payeeIds?, accrualIds?})` — свободные начисления по фильтру, сгруппированные по врачам, с предупреждениями.
- `createSheet(...)` — черновик.
- `approveSheet(id)` — **в одной транзакции**: присвоить номер (`ВВ-ГГГГ-ММ-NNN`), записать `snapshot`, проставить `sheetId` и `status = locked` всем начислениям, посчитать строки.
- `dissolveSheet(id, reason)` — только если нет ни одной выплаты; начисления возвращаются в `free`.
- `excludeAccruals(sheetId, ids)` — только для черновика.

Жёсткие проверки на уровне сервиса: запрет записи в `locked`/`paid`; отбор только `status = free AND sheetId IS NULL`.

**Готово, когда:** проходят Т11, Т13, Т14, Т15; повторное включение уже выплаченного начисления в другую ведомость невозможно ни через API, ни через интерфейс.
