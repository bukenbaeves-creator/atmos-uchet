# ATMOS — приложение учёта клиники

Клиент-серверное веб-приложение для клиники пластической хирургии: пациенты, консультации,
операции, платежи, склад расходных материалов, KPI менеджеров. **Приложение работает в
клинике с реальными данными** — все доработки должны быть обратно совместимы.

## Стек и запуск

- **Сервер:** Node 20 + Express + TypeScript + Prisma + PostgreSQL 16 (`server/`)
- **Клиент:** React 18 + TypeScript + Vite + Tailwind + TanStack Query + Recharts (`client/`)
- **Запуск:** `docker compose up --build` (клиент :5173, API :4000)
- **Прод:** Render, один web-сервис (Express отдаёт API и собранный фронтенд), см. `DEPLOY.md`

## Критическое ограничение: миграции БД

Прод стартует командой из `Dockerfile`:

```
npx prisma db push && npx prisma db seed && npx tsx src/index.ts
```

`db push` идёт **без** `--accept-data-loss`. Отсюда:

- Только **аддитивные** изменения схемы: новые модели, новые поля.
- Новое поле в существующей модели — **только** `nullable` или с `@default`.
- **Никаких** переименований и удалений существующих полей и моделей.
- Проверять изменения на копии базы, а не на рабочей.

## Что нельзя менять без явного согласования

| Файл / поведение | Почему |
|---|---|
| `server/src/services/compute.ts` | `computeOperation` и `round2` — основа кассы, дашборда и KPI |
| `server/src/services/kpi.service.ts` | Логика KPI менеджеров, не пересекается с выплатами врачам |
| `Operation.surgeon`, `Operation.anesthesiologist` | Используются в фильтрах, экспорте и отчётах. Даже после появления модели участников операции эти поля должны продолжать заполняться синхронно |
| Ответы существующих маршрутов `/api/*` | Поля можно добавлять, менять и удалять — нельзя |
| Сид демо-данных | В проде демо не создаётся, это поведение сохранить |

## Обязательные паттерны

**Сервер:**

- Роутер сущности — через фабрику `makeCrudRouter(cfg)` из `server/src/crud.ts` (soft-delete, аудит, RBAC уже внутри).
- Любой ответ клиенту — через `serialize(...)` (`Decimal` → number, `Date` → ISO).
- Ошибки — `throw notFound('…')` / `badRequest` / `forbidden` из `lib/http.ts`, обработчики оборачивать в `asyncHandler`.
- Права — `requireAuth` + `requireRole(...)` / `requireAdmin` **на сервере**, не только в интерфейсе.
- Аудит — `writeAudit(req, {...}, tx)` в той же транзакции, что и изменение.
- Деньги — `Decimal @db.Decimal(14,2)`, округление только через `round2()`.
- Даты — UTC-полночь, сравнения полуоткрытым интервалом `[from, toExclusive)` (образец — `kpi.service.ts`).
- Все выборки — с `deletedAt: null`.

**Клиент:**

- Запросы — `useList(entity, params)` и `useCrudMutations(entity)` из `src/api/hooks.ts`; новые ключи инвалидации добавлять в `RELATED_KEYS`.
- Маршруты — `src/App.tsx` (с `RequireAdmin` / `RequireRole`), меню — `SECTIONS` в `src/components/Layout.tsx`.
- Таблицы — `@tanstack/react-table`, графики — `recharts`. Новые библиотеки для этого не подключать.

**Язык:** интерфейс, сообщения об ошибках, комментарии в коде и сообщения коммитов — на русском.

## Роли

- `admin` — полный доступ, справочники, аудит, мягкое удаление и восстановление.
- `operator` — ввод данных; правит только свою запись и только в день её создания.
- `nurse` — только модуль склада и расходов, денежные разделы недоступны.

## Текущая задача: модуль «Выплаты врачам»

Документы в `docs/`:

- `ТЗ_Выплаты_врачам_v1.4.md` — что делаем и почему: модели расчёта, конструктор компонентов,
  событийная модель начислений, ведомости, реестр по врачу, дашборд, приёмочные тесты с реальными цифрами.
- `План_разработки_v1.0.md` — как делаем: 7 этапов, 28 задач, у каждой файлы и критерий приёмки.
- `Схема_БД_модуль_выплат.prisma` — **готовые определения всех моделей Prisma для модуля**.
  Это авторитетный источник схемы: блоки копируются в `server/prisma/schema.prisma` как есть.
  Не выводить модели из текста ТЗ и не придумывать имена полей.
- `Прототип_ведомость_и_дашборд.html`, `Прототип_конструктора_выплат.html` — интерактивные макеты
  интерфейса, открываются в браузере. Ориентир по структуре экранов и таблиц.

**Порядок работы:** задачи выполняются строго по возрастанию идентификатора (`Э0-1 → Э0-2 → …`).
Переход к следующей задаче — только после выполнения блока «Готово, когда» предыдущей.
Один этап — один коммит или серия коммитов с общим префиксом (`Выплаты: …`).
Работать в отдельной ветке от `main`.

Если задача противоречит существующему коду — не переписывать существующий код, а остановиться и спросить.
